## 实验七：写时复制（COW）

### 观察结果

#### 7.1 COW机制原理

**写时复制（Copy-on-Write）工作流程：**

```
1. fork()系统调用
   ├── 复制父进程的页表到子进程
   ├── 父子进程页表项都指向相同的物理页
   └── 页表项标记为只读

2. 读取共享页面
   └── 直接访问，不触发任何异常

3. 写入共享页面
   ├── 触发页错误（Page Fault）
   ├── 内核检查是否为COW页面
   ├── 分配新的物理页
   ├── 复制原页面内容到新页
   ├── 更新进程页表指向新页
   └── 重新执行写操作
```

#### 7.2 简单COW验证

```
父进程分配 100 MB 内存，填充字符 'P'

[子进程] 刚fork，数据: 'P' (与父进程共享)
[子进程] 修改前10页后:
  第0页: 'C' (已修改)
  第100页: 'P' (未修改，仍共享)

[父进程] 子进程退出后:
  第0页: 'P' (未被修改！)
  结论: COW保护了父进程的内存
```

#### 7.3 详细内存分析

**fork前（父进程）：**
```
VmRSS:     103,892 KB
共享内存:  1,436 KB
私有内存:  102,520 KB
```

**fork后（子进程修改前）：**
```
VmRSS:     103,348 KB
共享内存:  103,500 KB  ← 大部分内存共享！
私有内存:  40 KB
```

**子进程修改100MB后：**
```
VmRSS:     103,540 KB
共享内存:  1,100 KB    ← 共享内存减少
私有内存:  102,440 KB  ← 私有内存增加（COW复制）
```

#### 7.4 逐页PFN分析

**Fork后，修改前（父子共享相同PFN）：**
```
父进程/子进程 页0: pfn=0x8431a
父进程/子进程 页1: pfn=0x97ece
父进程/子进程 页2: pfn=0x3df52
...
```

**子进程修改后（PFN改变，COW触发）：**
```
子进程 页0: pfn=0x30a31  ← 新PFN！
子进程 页1: pfn=0x7c23   ← 新PFN！
...

父进程 页0: pfn=0x8431a  ← 保持不变
父进程 页1: pfn=0x97ece  ← 保持不变
...
```

**结论**：子进程修改页面后，获得了新的物理页帧号(PFN)，而父进程的PFN保持不变，验证了COW机制。

#### 7.5 缺页统计

| 阶段 | 子进程Minor faults |
|------|-------------------|
| Fork后 | 26 |
| 修改100MB后 | 25,628 |
| COW触发的缺页 | 25,602 |

每修改一页触发一次缺页中断，100MB = 25,600页，与实际数据吻合。

### COW优势

1. **fork()速度快**：只复制页表，不复制物理内存
2. **节省内存**：未修改的页面共享，减少物理内存占用
3. **按需复制**：只复制实际修改的页面
4. **支持exec优化**：如果fork后立即exec，完全不需要复制

### 遇到的问题与解决

1. **/proc/pid/pagemap需要root权限**
   - 解决：使用sudo运行exp7_cow_pages程序

2. **smaps解析**
   - 通过读取Shared/Private字段分析COW效果

### 思考题

1. **为什么COW能提高fork性能？**
   - fork只需复制页表（几KB到几MB），而非所有内存
   - 100MB内存的fork几乎瞬间完成

2. **什么时候COW会失败？**
   - 内存不足无法分配新页时
   - 超过进程内存限制

3. **如何避免不必要的COW？**
   - 使用MAP_SHARED而非MAP_PRIVATE
   - fork后尽快exec（不修改共享内存）

### 关键发现

1. **PFN可视化验证**：通过pagemap可以看到子进程修改后PFN确实改变了
2. **共享内存变化**：fork后共享内存从1MB增加到103MB，修改后又降回1MB
3. **缺页计数验证**：每修改一页触发一次COW缺页
